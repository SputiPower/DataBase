# DataBase

REST API проект для приёма, просмотра и условного редактирования данных о горных перевалах.

Проект реализован на Python с использованием FastAPI, SQLAlchemy и PostgreSQL. В первом спринте была реализована отправка новой записи о перевале, а во втором спринте добавлены методы просмотра, редактирования и выборки записей пользователя по email.

Дополнительные материалы по архитектуре и проектным решениям:

- `docs/database_analysis.md`
- `docs/architecture.md`
- `docs/sprint_1_solution.md`

## Задача проекта

Сервис принимает данные о горных перевалах от пользователей мобильного приложения, сохраняет их в базе данных и предоставляет API для дальнейшей работы с этими записями.

Основная бизнес-логика:

- пользователь может отправить новую заявку на перевал
- пользователь может получить полную информацию о заявке по `id`
- пользователь может получить список всех своих заявок по `email`
- пользователь может отредактировать заявку только если её статус модерации равен `new`
- данные пользователя в PATCH не редактируются

## Что реализовано в спринте 1

- спроектирована и реализована нормализованная PostgreSQL-схема
- добавлены таблицы `users`, `mountain_passes`, `pass_coordinates`, `pass_levels`, `pass_images`
- реализован статус модерации через PostgreSQL `ENUM`
- реализован `POST /submitData`
- добавлена валидация входного JSON
- реализовано транзакционное сохранение всей заявки
- добавлена обработка ошибок
- настроено подключение к БД через `.env`

## Что реализовано в спринте 2

- `GET /submitData/{id}` для получения полной записи по идентификатору
- `PATCH /submitData/{id}` для редактирования записи со статусом `new`
- `GET /submitData?user__email=<email>` для получения списка всех заявок пользователя
- улучшена Swagger/OpenAPI документация
- добавлены тесты для основных API-сценариев
- обновлена документация в `README.md`

## Почему выбран этот стек

Для проекта выбран стек `FastAPI + SQLAlchemy + PostgreSQL`, потому что он хорошо подходит для разработки REST API и позволяет сделать решение аккуратным, расширяемым и удобным для дальнейшего развития.

Почему именно так:

- `FastAPI` даёт удобный способ описывать API, валидацию и Swagger документацию
- `Pydantic` используется для строгой проверки входных и выходных данных
- `SQLAlchemy 2.0` позволяет аккуратно описать модели и отделить логику работы с БД
- `PostgreSQL` хорошо подходит для хранения структурированных данных, индексов, ограничений и enum-типов
- `psycopg` v3 используется как современный драйвер PostgreSQL

Для проекта выбран синхронный вариант реализации, потому что:

- он проще для учебно-практического backend-проекта
- не перегружает архитектуру лишней асинхронной сложностью
- полностью подходит для текущего объёма API
- позволяет делать предсказуемые транзакционные операции

## Структура базы данных

В проекте используется нормализованная структура базы данных.

Основные таблицы:

- `users` — данные пользователя
- `mountain_passes` — основная информация о перевале
- `pass_coordinates` — координаты и высота
- `pass_levels` — уровни сложности по сезонам
- `pass_images` — фотографии перевала

### Почему структура была улучшена

Данные не хранятся целиком в одном `json`, потому что это неудобно для реальной реляционной базы данных.

Преимущества текущей схемы:

- есть внешние ключи между сущностями
- можно задавать ограничения и индексы
- удобно выполнять выборки и фильтрацию
- проще расширять проект дальше
- фотографии хранятся как отдельная коллекция записей

## Статусы модерации

У перевала есть поле `status`.

Поддерживаемые значения:

- `new`
- `pending`
- `accepted`
- `rejected`

Для хранения статуса выбран PostgreSQL `ENUM`, потому что:

- набор статусов фиксирован
- база данных сама защищает от невалидных значений
- такое решение удобно для модерации и фильтрации

Новая запись всегда создаётся со статусом `new`.

## Хранение изображений

В первом и втором спринте изображения сохраняются в PostgreSQL в поле `BYTEA`.

Почему выбран такой вариант:

- это проще для первого этапа проекта
- данные изображения уже приходят внутри JSON
- можно сохранить запись и изображения одной транзакцией
- не требуется отдельное файловое хранилище

В будущем изображения можно вынести в S3, MinIO или другое object storage, а в базе оставить только метаданные и URL.

## API методы

### 1. POST `/submitData`

Создаёт новую запись о перевале.

Принимает:

- основную информацию о перевале
- данные пользователя
- координаты
- уровни сложности
- фотографии

Новая запись автоматически получает статус `new`.

#### Пример запроса

```json
{
  "beauty_title": "пер. ",
  "title": "Пхия",
  "other_titles": "Триев",
  "connect": "",
  "add_time": "2021-09-22 13:18:13",
  "user": {
    "email": "qwerty@mail.ru",
    "fam": "Пупкин",
    "name": "Василий",
    "otc": "Иванович",
    "phone": "+7 555 55 55"
  },
  "coords": {
    "latitude": "45.3842",
    "longitude": "7.1525",
    "height": 1200
  },
  "level": {
    "winter": "",
    "summer": "1А",
    "autumn": "1А",
    "spring": ""
  },
  "images": [
    {
      "data": "aGVsbG8=",
      "title": "Седловина"
    },
    {
      "data": "d29ybGQ=",
      "title": "Подъём"
    }
  ]
}
```

#### Успешный ответ

```json
{
  "status": 200,
  "message": null,
  "id": 42
}
```

#### Ошибка валидации

```json
{
  "status": 400,
  "message": "Отсутствует обязательное поле title",
  "id": null
}
```

```json
    "fam": "Пупкин",
    "name": "Василий",
    "otc": "Иванович",
    "phone": "+7 555 55 55"
  },
  "coords": {
    "latitude": "45.3842",
    "longitude": "7.1525",
    "height": 1200
  },
  "level": {
    "winter": null,
    "spring": null,
    "summer": "1А",
    "autumn": "1А"
  },

    {
      "data": "aGVsbG8=",
```


### 3. PATCH `/submitData/{id}`

Обновляет существующую запись.

PATCH принимает тот же JSON, что и `POST /submitData`.

#### Ограничения PATCH

Редактирование разрешено только если:

- запись существует
- её статус равен `new`

Редактировать нельзя поля пользователя:

- `email`
- `fam`
- `name`
- `otc`
- `phone`

Если в PATCH приходит изменённый блок пользователя, API возвращает ошибку.  
Выбран именно такой вариант, а не молчаливое игнорирование, потому что это безопаснее и честнее по отношению к клиенту: клиент сразу видит, что попытка редактирования запрещённого поля не будет принята.

#### Успешный ответ

```json
{
  "state": 1,
  "message": null
}
```

#### Если статус не `new`

```json
{
  "state": 0,
  "message": "Редактирование запрещено, так как статус записи не new"
}
```

#### Если попытались изменить данные пользователя

```json
{
  "state": 0,
  "message": "Редактирование данных пользователя запрещено"
}
```

### 4. GET `/submitData?user__email=<email>`

Возвращает список всех записей, которые пользователь когда-либо отправлял по указанному email.

Для каждой записи возвращаются:

- `id`
- `title`
- `beauty_title`
- `other_titles`
- `status`
- `add_time`
- `created_at`
- `updated_at`

Если записей нет, возвращается пустой список.

#### Пример ответа

```json
[
  {
    "id": 1,
    "title": "Пхия",
    "beauty_title": "пер.",
    "other_titles": "Триев",
    "status": "new",
    "add_time": "2021-09-22T13:18:13",
    "created_at": "2026-03-19T18:00:00+03:00",
    "updated_at": "2026-03-19T18:00:00+03:00"
  }
]
```

## Обработка ошибок

В проекте предусмотрена обработка следующих ситуаций:

- неверный JSON
- отсутствие обязательных полей
- ошибка валидации path/query/body параметров
- запись не найдена
- редактирование запрещено из-за статуса
- попытка изменить данные пользователя
- ошибка подключения к базе данных
- ошибка сохранения данных
- внутренняя ошибка сервера

Ошибки возвращаются в безопасном и понятном формате без раскрытия внутренней реализации приложения.

## Транзакционность

Операции создания и редактирования записи выполняются в рамках одной транзакции.

Это означает, что:

- либо сохраняется вся запись целиком
- либо при ошибке изменения откатываются полностью

За счёт этого в базе не остаётся частично сохранённых данных.

## Деплой

Проект задеплоен на Sber Cloud на отдельную Ubuntu VM.

Что используется в текущем деплое:

- Ubuntu 22.04
- PostgreSQL на том же сервере
- FastAPI + Uvicorn
- `systemd` для автозапуска приложения
- `nginx` как reverse proxy

Схема запуска:

1. на сервере устанавливаются `python3-venv`, `postgresql`, `nginx`
2. создаётся PostgreSQL база данных и пользователь приложения
3. на сервер копируется проект и создаётся `.env`
4. применяются SQL-таблицы из `sql/schema.sql`
5. FastAPI запускается через `systemd`
6. `nginx` проксирует внешний HTTP-трафик на `127.0.0.1:8000`

Если переносить проект на другой сервер, минимально понадобятся:

- Python 3.12+
- PostgreSQL
- env-переменные:
  - `FSTR_DB_HOST`
  - `FSTR_DB_PORT`
  - `FSTR_DB_LOGIN`
  - `FSTR_DB_PASS`
  - `FSTR_DB_NAME`

Команда локального запуска приложения:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```
