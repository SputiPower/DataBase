# Архитектурное решение

## Слои приложения

### API layer
- принимает HTTP-запрос
- валидирует контракт через Pydantic
- возвращает унифицированный JSON-ответ
- не содержит SQL-логики

### Service layer
- оркестрирует сценарий `submitData`
- управляет транзакционной записью
- содержит бизнес-правила уровня приложения

### Repository layer
- работает с ORM-моделями
- инкапсулирует доступ к БД
- разбивает сохранение на логические операции: пользователь, перевал, координаты, уровни, изображения

### Core / Infrastructure
- конфигурация из env
- создание engine/session
- базовые доменные исключения

## Схема связей

### `users -> mountain_passes`
- связь `1:N`
- один пользователь может отправить много перевалов

### `mountain_passes -> pass_coordinates`
- связь `1:1`
- координаты вынесены отдельно, чтобы держать доменную сущность чистой и при желании расширять геоданные отдельно

### `mountain_passes -> pass_levels`
- связь `1:1`
- уровень сложности по сезонам вынесен отдельно, чтобы не раздувать основную таблицу и иметь гибкость для следующего этапа

### `mountain_passes -> pass_images`
- связь `1:N`
- у одного перевала несколько фотографий с сохранением порядка

## Почему статус хранится в основной таблице перевалов

Статус относится к жизненному циклу самой заявки, а не к вложенным данным. Поэтому он хранится прямо в `mountain_passes`:

- проще фильтровать модерацию
- проще строить индексы
- проще реализовать следующий спринт с workflow-логикой

## Почему транзакция на весь submitData

Запрос должен быть атомарным:

- если пользователь создался, а изображения не сохранились, система не должна оставаться в битом состоянии
- все связанные сущности должны появляться вместе или не появляться вообще

Поэтому в сервисе используется единая транзакция на всю операцию `submit`.
