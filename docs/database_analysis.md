# Анализ исходной структуры БД

## Что было в исходной схеме плохо

### 1. Нарушена нормализация
- Таблица `pereval_added` хранит почти всю бизнес-сущность в `raw_data json`.
- Пользователь, координаты, уровни сложности и часть изображений не выделены в отдельные таблицы.
- Из-за этого невозможно нормально навесить ограничения, индексы и связи на отдельные поля.

### 2. JSON используется неудачно
- `raw_data` превращает реляционную БД в слабоструктурированное хранилище.
- `images json` дублирует смысл отдельной таблицы `pereval_images`, но без явной связи.
- Валидация данных переносится из БД в приложение и становится ненадёжной.

### 3. Нет явных связей между сущностями
- `pereval_images` никак не связан с `pereval_added` внешним ключом.
- Нельзя гарантировать, что изображения действительно принадлежат существующему перевалу.
- Нельзя каскадно удалять зависимые записи и поддерживать целостность.

### 4. Ошибки в проектировании sequence/PK
- Для `pereval_images.id` используется `pereval_added_id_seq`, что выглядит как явная ошибка проектирования.
- Это повышает риск коллизий и затрудняет сопровождение.

### 5. Нет ограничений на данные
- Нет `NOT NULL` для действительно обязательных полей.
- Нет `CHECK` для широты, долготы, высоты.
- Нет ограничений на допустимые статусы, хотя статус вообще отсутствует.

### 6. Нет нужных индексов
- В выгрузке прямо указано, что индексы отсутствуют.
- Без индексов плохо масштабируются фильтрация по пользователю, статусу, времени добавления, связи с изображениями.

### 7. Структура неудобна для развития
- Трудно добавлять workflow-механику модерации.
- Трудно делать аналитику по пользователям, сезонам, сложности и географии.
- Трудно строить API на устойчивой контрактной модели данных.

## Улучшенная схема

Для первого спринта выбрана нормализованная модель:

- `users` — отправители данных
- `mountain_passes` — основная сущность перевала
- `pass_coordinates` — координаты и высота в отдельной 1:1 таблице
- `pass_levels` — уровни сложности по сезонам в отдельной 1:1 таблице
- `pass_images` — фотографии в связи 1:N

## Почему изображения хранятся в PostgreSQL `BYTEA`

Для первого спринта это практичное решение:

- не нужно поднимать отдельное файловое хранилище
- транзакция охватывает и метаданные, и изображения
- нет риска, что запись в БД создалась, а файл не сохранился

Для следующего этапа проект можно безболезненно перевести на object storage (S3/MinIO/Cloud storage) и хранить в БД уже только метаданные и URL.
